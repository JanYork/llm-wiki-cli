# LWC Todo and Current Plan for Agents - Logic Design

Status: `executable`

## Domain Model and Identity

### Todo

- Identity: 32 lowercase hexadecimal characters generated by SQLite random bytes;
  title is mutable and never an identity.
- Required: non-empty title, revision 1, state `open`.
- Optional: deduplicated tags, cue, detail, request ID.
- Terminal information: `done` requires result; `cancelled` requires reason.
- Ownership: exactly one project or global Store; cross-scope reads retain origin.

### Plan

- Identity: same opaque ID form as Todo; title/tags are search indexes, not keys.
- Required: title, objective, `done_when`, 1..=100 ordered steps.
- Step identity: stable within a Plan and never reused after revision.
- Active focus: one `in_progress` or `blocked` step. A completed Plan has no focal or
  non-terminal step. An abandoned Plan may retain unfinished steps for inspection.
- Revision: starts at 1 and increments once per successful mutation; one compact
  history row records the same revision and action.

## Core Rules

- `RULE-IDENTITY-01` Normalize required text by trim; reject empty/control-only text,
  oversized bounded fields, duplicate step IDs, and unknown JSON fields before write.
- `RULE-TAG-01` Trim tags, validate 1..=128 Unicode characters with no controls,
  deduplicate exact matches, preserve Unicode/case, and sort response tags
  lexicographically. Todo/Plan tags never mutate Wiki `tags` or `page_tags`.
- `RULE-IDEMPOTENCY-01` A retained `request_id` plus identical canonical create input
  returns the original entity with `created=false`; different input returns a request
  conflict. Missing/different request IDs create distinct entities.
- `RULE-REVISION-01` Existing-entity mutations require `--if-revision`. A mismatch
  returns the current revision without changing canonical rows, FTS, history, or
  operation log.
- `RULE-TODO-01` Todo state transitions are `open -> done`, `open -> cancelled`, and
  `done|cancelled -> open`; update is allowed only while `open`.
- `RULE-TODO-02` Repeating a transition already achieved with identical result/reason
  returns `action=unchanged`; different terminal data requires reopen followed by the
  intended transition.
- `RULE-PLAN-01` Plan create marks the first step `in_progress`, all later steps
  `pending`, and appends `created` history at revision 1.
- `RULE-PLAN-02` `advance` atomically completes the focal in-progress step with a
  non-empty result and selects the next pending step as `in_progress`. It rejects a
  blocked/non-focal `--done` ID or invalid/missing `--next`.
- `RULE-PLAN-03` `block` changes only the focal `in_progress` step to `blocked`, stores
  a reason in both step and history, and leaves top-level state `active`.
- `RULE-PLAN-04` `revise` requires a reason. It preserves completed/skipped steps,
  marks replaced focal/future steps `skipped` with that reason, appends 1..=100 new
  uniquely identified future steps, and selects exactly one new focal step.
- `RULE-PLAN-05` `complete` succeeds only when every step is `completed` or `skipped`,
  result/evidence are non-empty, and `--done-when-checked` is present. The CLI validates
  the assertion, not its truth.
- `RULE-PLAN-06` `abandon` accepts an active Plan with a non-empty reason, preserves
  all steps/history, and is terminal in v1; Plan reopening is not supported.
- `RULE-BRIEF-01` Brief returns at most 20 completed/skipped result summaries plus one
  focal and one next step; if more terminal steps exist, it reports omitted count.
- `RULE-READ-01` Exact list order is `updated_at DESC, id ASC`; FTS order is relevance,
  then `updated_at DESC`, then ID. Cross-scope merge applies the same total order and
  then the requested global limit.
- `RULE-AUDIT-01` Every successful mutation updates canonical rows, FTS, and one
  operation/history entry in the same transaction. Reads and idempotent unchanged
  responses add no operation.
- `RULE-BOUNDARY-01` Todo/Plan commands never execute work, infer semantic links,
  mutate Wiki/memory/Work, delete records, or expose raw chain-of-thought.

## State Transitions

### Todo

```text
          done(result)
open --------------------> done
  |                         |
  | cancel(reason)          | reopen
  v                         v
cancelled ----------------> open
              reopen
```

- `update`: `open -> open`, revision +1 only when content changes.
- `done`: `open -> done`, closes with result.
- `cancel`: `open -> cancelled`, closes with reason.
- `reopen`: `done|cancelled -> open`, clears terminal result/reason/closed time.

### Plan and step focus

```text
create: [in_progress, pending, ...]
advance: completed + next pending -> in_progress
block:   in_progress -> blocked
revise:  blocked/in_progress/pending -> skipped; new focal -> in_progress
complete: all completed/skipped + checked evidence -> Plan completed
abandon: active -> abandoned (steps preserved)
```

- Top-level `completed` and `abandoned` are terminal in v1.
- `blocked` is a step status, not a Plan terminal state.
- Revision/history increments once for create, advance, block, revise, complete, or
  abandon, regardless of how many step rows change inside that transaction.

## Data Semantics

- Null means “not supplied”; empty strings are rejected rather than normalized to null.
- Clearing optional Todo cue/detail is explicit; omission means leave unchanged.
- Tags are sets; step and constraint order is meaningful and stored by ordinal.
- Times are UTC RFC3339 strings generated inside SQLite transactions.
- `closed_at` exists only for Todo done/cancelled and Plan completed/abandoned.
- Reopen clears Todo terminal payloads to avoid stale result/reason claims.
- Plan completed/skipped step title/result/verify facts are immutable. A later Plan
  correction is a new Plan; v1 has no reopen or history rewrite.
- FTS is a derived index only. `show`, transition checks, and brief read canonical
  tables; corrupted/missing FTS never becomes state truth.
- Project and global IDs are opaque and statistically unique, but exact-ID reads still
  require an explicit scope to prevent accidental cross-store mutation.
- Pagination is bounded: `limit` 1..=1000 and non-negative offset. `brief` has its own
  fixed completed-step cap from `RULE-BRIEF-01`.

## Primary Flow

### `FLOW-TODO-CREATE`

1. Reject `--changeset` and `--scope all`; resolve one Store.
2. Parse flags or strict JSON and normalize fields/tags.
3. Start immediate transaction; compute canonical fingerprint.
4. Resolve `request_id`: unchanged replay or conflict, otherwise allocate ID.
5. Insert Todo/tag rows, index FTS, record `todo_add`, commit.
6. Return `created`, origin scope, entity, and revision.

### `FLOW-TODO-QUERY`

1. Resolve one or two read-only stores for list/search.
2. Apply indexed state/tag filter and bounded FTS query when applicable.
3. Attach scope, merge total order, then limit; return pagination metadata.
4. `show` instead resolves one exact store and returns the complete canonical entity.

### `FLOW-TODO-TRANSITION`

1. Resolve exact store; validate ID, revision, required result/reason.
2. Start immediate transaction and reload state/revision.
3. Apply `RULE-TODO-01` and idempotency rule.
4. Update canonical row/FTS as needed, record operation, commit, return new revision.

### `FLOW-PLAN-CREATE`

1. Resolve exact scope and parse flags/strict JSON.
2. Validate objective, done criteria, constraints, 1..=100 steps, and tags.
3. Start transaction; resolve request id/fingerprint; allocate Plan and step IDs.
4. Insert Plan, normalized children, revision-1 history, FTS, and operation.
5. Commit and return the active Plan with first focal step.

### `FLOW-PLAN-RESUME`

1. `current` discovers bounded active Plan headers by tag/title index.
2. Agent selects an exact Plan ID and scope.
3. `brief` reads canonical Plan, terminal summaries, focal, next, and revision.
4. No write, history entry, or Hook mutation occurs.

### `FLOW-PLAN-ADVANCE`

1. Resolve exact Plan and compare revision inside an immediate transaction.
2. Verify `--done` is the focal in-progress step and `--next` matches one pending step
   when one exists.
3. Complete focal with result; activate next; increment Plan revision once.
4. Append `advanced` history, update FTS/operation, commit, return a new brief.

### `FLOW-PLAN-REVISE`

1. Resolve exact active Plan and compare revision.
2. Parse strict revision payload and validate explicit reason/new step set/focal.
3. Preserve terminal steps; mark replaced non-terminal steps skipped with reason.
4. Add new steps, activate one focal, increment revision, append history, update FTS.
5. Commit and return a new brief showing the replan reason/revision.

### `FLOW-PLAN-COMPLETE`

1. Resolve Plan and compare revision.
2. Assert all steps terminal, evidence/result non-empty, and checked flag present.
3. Set Plan completed/closed fields, increment revision, append history/operation.
4. Commit and return completed Plan; no Wiki/memory write follows.

### `FLOW-SCOPE-READ`

1. Allow `all` only for the five documented discovery commands.
2. Query each current store read-only; never migrate from a cross-scope read.
3. Attach scope before deterministic merge and global pagination.

### `FLOW-HOOK-READINESS`

1. Reuse the existing lifecycle Hook invocation and resolve only host-authorized stores.
2. Open current stores read-only; never initialize or migrate from the Hook.
3. Count indexed open Todos and active Plans, or return bounded readiness diagnostics.
4. Emit counts, at most three due Todo summaries, and one bounded active Plan continuity
   summary; do not emit Todo cue/detail, Plan reasoning/evidence fields, or write state.

### `FLOW-SKILL-INSTALL`

1. Resolve existing target's `using-lwc` path and its skill-root parent.
2. Preflight all three canonical bundle paths with current manifest ownership rules.
3. Snapshot user bytes, atomically write canonical bundles, and save one manifest.
4. Refresh replaces only owned bytes; uninstall restores/removes exactly tracked paths.

## Error and Edge Cases

- Missing current store, legacy read-only store, unauthorized `@PATH`, invalid UTF-8,
  oversized JSON, unknown JSON field, empty title/tag/step, >100 steps, invalid limit,
  and `--scope all` mutation fail before any write.
- Duplicate tags collapse; duplicate step IDs, duplicate ordinals, or a focal ID not in
  the payload fail atomically.
- `request_id` conflict and revision conflict never partially change canonical data,
  FTS, history, or operations.
- `advance` cannot skip a pending step implicitly; `revise` is the explicit route.
- A blocked step cannot be advanced as completed until `revise` establishes a new
  focal plan. Abandon remains available.
- A Plan with no pending step after the last advance remains active until explicit
  complete validates result/evidence.
- Read-only Hook failures are represented as readiness diagnostics and never trigger
  migration, create, update, or recovery work.
- Installer collision with user-owned sibling Skill bytes follows existing manifest
  conflict/restore behavior; it must not overwrite without ownership evidence.

### `FLOW-CAPABILITY-GATE`

1. Resolve the effective setting from built-in, global, then project configuration.
2. Reject disabled exact-scope commands with `todo_disabled` or `plan_disabled`.
3. For `--scope all`, query only enabled stores and fail when none qualify.
4. During Hook generation, omit disabled capability fields.
5. During Skill use, inspect `config show`; stop when disabled and never auto-enable.

- `RULE-CONFIG-01` Capability detection is not enablement consent. Enabling Todo and
  Plan are independent explicit configuration mutations.

### `FLOW-PLAN-TRACK`

1. When Plan is enabled, select the most recently updated active Plan deterministically.
2. Count completed, terminal, and total steps.
3. Select the focal in-progress/blocked step and first pending step by ordinal.
4. Bound titles to 500 Unicode scalars and emit revision plus an exact brief command.

- `RULE-TRACK-01` Tracking is a read-only continuity cue, not authority to mutate; the
  Agent reloads `plan brief` before using revision CAS.

### `FLOW-TODO-CHILD-TIME`

1. Normalize an optional direct parent ID and RFC3339 target time before fingerprinting.
2. Validate parent existence inside the create transaction; never reparent on update.
3. Expose direct child summaries and allow `--parent` filtering without recursive loading.
4. If Todo is enabled, select due open rows by oldest creation time, take three, and
   report `total - returned` without exposing cue/detail.

- `RULE-TODO-CHILD-01` Parentage has no lifecycle or dependency semantics.
- `RULE-TODO-TIME-01` Target time is scheduling metadata; reminders never mutate state.
